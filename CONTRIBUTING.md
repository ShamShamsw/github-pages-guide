# 🤝 Contributing to the GitHub Pages Guide

First off, thank you for considering contributing to this beginner's guide! Your help makes this resource better for students and learners everywhere.

## 📋 How Can I Contribute?

### 🐛 Reporting Bugs or Issues

Found a typo, broken link, or incorrect information? Here's how to report it:

1. **Check existing issues** to see if it's already been reported
2. **Open a new issue** with a clear title
3. **Describe the problem** with as much detail as possible:
   - What's incorrect or unclear?
   - Where is it located? (file name, section, line number)
   - What should it say instead?

### ✨ Suggesting Enhancements

Have an idea for improving the guide? We'd love to hear it!

1. **Check existing issues** to avoid duplicates
2. **Open a new issue** tagged with "enhancement"
3. **Describe your suggestion:**
   - What would you like to add or change?
   - Why would it help beginners?
   - Do you have examples or references?

### 📝 Submitting Changes

Ready to make changes yourself? Here's the process:

#### 1. Fork the Repository
Click the "Fork" button in the top right of the repository page.

#### 2. Clone Your Fork
```bash
git clone https://github.com/YOUR-USERNAME/github-pages-guide.git
cd github-pages-guide
```

#### 3. Create a Branch
```bash
git checkout -b fix/description-of-fix
# or
git checkout -b feature/description-of-feature
```

**Branch naming conventions:**
- `fix/` — Bug fixes, typos, broken links
- `feature/` — New content or sections
- `docs/` — Documentation improvements

#### 4. Make Your Changes

Follow these guidelines:
- ✅ Keep the **beginner-friendly tone** — assume zero prior knowledge
- ✅ Use **clear, simple language** — avoid jargon when possible
- ✅ Add **examples** where helpful
- ✅ Keep formatting **consistent** with existing sections
- ✅ Test any code snippets or instructions
- ✅ Check for **spelling and grammar**

#### 5. Commit Your Changes
```bash
git add .
git commit -m "Fix: corrected DNS configuration steps in Section 4"
```

**Commit message guidelines:**
- Start with a verb: "Fix", "Add", "Update", "Remove"
- Be specific and concise
- Reference issue numbers if applicable: "Fix #12: update broken link"

#### 6. Push to Your Fork
```bash
git push origin fix/description-of-fix
```

#### 7. Open a Pull Request

1. Go to the original repository
2. Click "Pull Requests" → "New Pull Request"
3. Click "compare across forks" and select your branch
4. Fill out the PR template:
   - **Title:** Clear, descriptive summary
   - **Description:** What changed and why
   - **Related Issues:** Link any relevant issues

## ✅ Pull Request Guidelines

### Before Submitting
- [ ] I've read the existing guide to understand the style and tone
- [ ] I've tested any code examples or instructions
- [ ] I've checked for spelling and grammar errors
- [ ] My changes are focused and relevant to the guide's scope
- [ ] I've kept the beginner-friendly approach

### Content Standards
- **Clarity over brevity** — it's okay to be verbose if it helps beginners understand
- **Examples are encouraged** — show, don't just tell
- **Sequential instructions** — use numbered steps for processes
- **Accessibility matters** — use descriptive link text, alt text for images
- **Attribution** — credit sources when adding external information

### What We're Looking For
✅ **Good contributions:**
- Fixing typos, grammar, or broken links
- Clarifying confusing sections
- Adding helpful examples or screenshots
- Updating outdated information
- Improving step-by-step instructions
- Adding beginner-friendly explanations

❌ **What doesn't fit:**
- Advanced topics beyond a beginner's first site
- Overly technical jargon without explanation
- Commercial promotions or affiliate links
- Content not related to GitHub Pages

## 🎨 Style Guide

### Markdown Formatting
- Use `#` for main sections, `##` for subsections, `###` for sub-subsections
- Use **bold** for emphasis on important terms
- Use `code blocks` for file names, commands, and code
- Use emojis sparingly and consistently (match existing sections)
- Use `>` blockquotes for important notes

### Tone & Voice
- **Friendly and encouraging** — make learners feel supported
- **Patient and thorough** — explain "why" not just "how"
- **Assumption-free** — don't assume prior knowledge
- **Positive language** — focus on what learners *will* accomplish

### Code Examples
- Include **complete, working examples** (not just snippets)
- Add **comments** to explain what code does
- Test examples before submitting
- Use consistent indentation (2 spaces for YAML, 4 for HTML)

## 🔍 Review Process

1. **Automated checks** — GitHub Actions will run basic validation
2. **Maintainer review** — A project maintainer will review your PR
3. **Feedback** — You may be asked to make changes
4. **Approval** — Once approved, your PR will be merged!

**Expected timeline:** Most PRs are reviewed within 1-3 days.
